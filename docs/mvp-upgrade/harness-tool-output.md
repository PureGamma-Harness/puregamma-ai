# Research tools: model-visible evidence and run state

## Repository facts and reproduced gap

- Baseline: `5628f9655a428fecec1df0549a8414c8ff04009d`. Core V2 owns capability services and tool plugins; compatibility providers remain one-way adapters. No second runtime or cross-import of legacy application code is needed (`docs/architecture/HARNESS_CORE_V2.md`).
- `harness/plugins/tool-research/src/index.ts` registers six read-only tools. Providers return `ResearchDocument.payload`, including event summaries, evidence, source URLs, timestamps, health and evidence gaps. The old renderer returned only kind/time/source/degraded metadata.
- `harness/plugins/tool-research-runner/src/index.ts` registers create/status/cancel tools. The authenticated sandbox provider returns `payload.run_id`, actual `status`, errors, limits, metrics, figure references and bounded logs. The old renderers returned only timestamps, including a misleading generic queued/read label for an unavailable create response.
- The fixed `@deepseek-ai/dsh-tools@0.1.5-rc.2` contract separates canonical `value` from `content`: `defineTool` adapts/validates `execute` and `output.render`; the registry renders content after validating the value and returns both. Its `ToolExecutionResult.value` documentation explicitly says the value is execution-local and omitted from durable events. In matching `@deepseek-ai/dsh-agent-loop@0.1.5-rc.2`, `appendToolResult` persists `result.content`, and `buildRequest` takes messages from session derivation. Consequently native model messages lack the payload; programmatic tool calling can still read `result.value` and must retain it unchanged.
- Published SDK references: `dsh-tools/lib/types/index.d.ts:96` describes the native/model projection; `:389` describes execution-local values; `dsh-tools/lib/index.js:createSuccessResult` validates/freezes the canonical DTO and invokes the separate renderer. Matching `dsh-agent-loop/lib/index.js:697` persists only presentation content via `appendToolResult`, and `:1203` derives the next request messages. Its in-process `tools/result` observer is a distinct, non-durable consumer that still receives the canonical value.
- API schemas were inspected as evidence only: `apps/api/services/research_event_service.py` serializes stored event provenance, health and gaps; `apps/api/services/research_runner_service.py:serialize_research_run` reports authoritative state. This change does not import or alter those implementations.

## Context engineering choices

This is a bounded evidence projection at the existing tool seam, rather than another RAG index, orchestration framework or runtime. Current services already own retrieval and authoritative run state. A model needs the returned evidence, not a fabricated answer or new retrieval source.

The projection contains a document metadata object, the returned payload and an explicit projection report. Important availability/provenance fields are visited before narrative and other data. Health `overall` and snapshot time precede verbose source diagnostics. Each root branch receives at most 2400 serialized bytes and 64 nodes so one branch cannot consume the entire payload budget. Hard limits also cover string length, depth, collection width and total visited nodes, with valid JSON retained at every limit. Output stays within 8000 UTF-8 bytes, below the existing profile's 8192-character downstream pruning threshold (`harness/profile/cordis.patch.yml`). Logs preserve their latest tail; other strings preserve their ordered prefix.

Omission is explicit and does not mean absence in the underlying service. This is a partial context view when any limit is reached, so it does not promise every citation or event will fit. All source values remain lower-trust data; JSON quoting and a boundary instruction aid interpretation but do not claim to solve prompt injection. No request code is copied into the output, and figure references remain metadata rather than fetched binaries. The canonical service result is neither truncated nor mutated. Existing permission, budget, provider and retirement gates are untouched.

## Acceptance and offline evaluation

1. Within the explicit context budget, every research tool exposes real evidence text, citations, health, timestamp and evidence-gap fields when present; empty/unavailable sources remain empty/unavailable.
2. Create/status/cancel expose the actual returned run ID and status, including unavailable, failed, running and cancelled results. The requested operation never overrides returned state.
3. Native `content` contains the projection; canonical `value` is unchanged. Each tool invokes only its existing service method once, with the existing arguments/defaults. Rejected argument shapes do not reach services.
4. Large strings, arrays, deep/wide objects, hostile instruction text and Unicode produce bounded valid JSON with explicit omissions. Provenance and health receive priority; partial output never claims a complete result.
5. Offline replay uses the installed pinned SDK, source imports through `tsx`, and mock services only. Run from a clean dependency installation with `corepack pnpm install --no-frozen-lockfile`, then `corepack pnpm run research-output-check` in `harness/`. Architecture/retirement and applicable TypeScript/package bundle checks must also pass. Full repository/provider quality is outside this fixture's claims.
